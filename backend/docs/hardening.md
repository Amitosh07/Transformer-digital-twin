## Request metadata and errors

The ASGI request middleware records request_id, method, path, status and duration_ms.
It never reads or logs request bodies, query strings or telemetry measurements. A supplied
X-Request-ID is accepted when it is 1..128 ASCII letters/digits or `.`, `_`, `:`, `-`;
otherwise a UUID is generated. Every HTTP response carries X-Request-ID. CORS permits
this request header and exposes the response header to configured dashboard origins.

Safe error correlation preserves the shared envelope. For object details, request_id is
added; a null detail becomes an object containing request_id; string details become an
object with message and request_id. Validation details remain a list of the existing
location/message/type entries, followed by an object containing request_id.

```json
{"error":{"code":"INTERNAL_ERROR","message":"Internal server error","details":{"request_id":"demo-request-1"}}}
```

Unexpected service exceptions and HTTP errors with status >= 500 never expose exception
text or traceback/SQL parameters. The global unexpected handler logs only the exception
class, avoiding SQL parameter values in exception representations. Expected 4xx errors
retain useful public details. Standalone apps registering only the shared handlers remain
compatible when they have no request middleware/state.

## Readiness

GET `/health/ready` returns ReadinessOut. `/health` retains its previous status/body behavior.
Readiness is 503 until startup finishes and once shutdown begins. MQTT still stops before
the cached HTTP ML client closes; prior shutdown tests continue exercising this ordering.

Checks after startup:

- Database: SELECT 1, then compare all current Alembic revisions with the migration heads.
  The expected filesystem heads are cached; no engine is constructed per probe.
- Stub ML: ready without inference or network work.
- Python ML: import the configured module:function and verify it is callable. No inference
  function is called. The cached adapter/import path is reused.
- HTTP ML: probe ML_HTTP_URL with HEAD, falling back to GET only for 405/501. Each request
  uses the smaller of ML_TIMEOUT_SECONDS and 1 second for httpx operation timeouts. There
  are no retries or redirects; only response headers are inspected and no response body
  is downloaded. A 2xx response is ready; transport errors or other status
  codes are error. If both methods are unsupported, ML is explicitly unchecked.

A healthy database/schema with ML ready or explicitly unchecked returns 200. Unchecked
means the configured endpoint cannot be probed with these methods, rather than verified
inference availability. Any failed required check returns 503 with short, sanitized details.
No model prediction is generated by a probe.

```json
{"status":"ready","db":"ready","migrations":"ready","ml":"ready","details":{}}
```

An unapplied migration example (503):

```json
{"status":"not_ready","db":"ready","migrations":"error","ml":"ready","details":{"migrations":"Database revisions do not match migration heads"}}
```

## OpenAPI compatibility

OpenAPI has the Transformer Digital Twin title, canonical/proxy-risk description, version
from SCHEMA_VERSION and a contact-name placeholder. `/openapi.json` has a committed baseline
in `tests/snapshots/openapi.json`. The contract test detects removed/renamed paths, methods,
parameters, response status/content types and recursively resolved response fields (including
nested objects, arrays and maps). Additions are allowed. Negative tests prove that path,
parameter and response-field removal fails rather than silently regenerating the snapshot.

Regenerate deliberately after reviewing the contract change:

```powershell
$env:MQTT_ENABLED = "false"
$env:ML_BACKEND = "stub"
.venv/Scripts/python.exe scripts/snapshot_openapi.py
.venv/Scripts/python.exe -m pytest tests/hardening/test_contract.py -q
git diff -- tests/snapshots/openapi.json
```

The generator only writes the snapshot; it does not stage or commit it. Review before
committing. SCHEMA_VERSION remains the canonical version from configuration.

## Source and wording guards

`tests/hardening/test_guards.py` scans app/, alembic/, scripts/, the committed OpenAPI JSON
and freshly generated OpenAPI, rejecting excluded measurement names (case/underscore variants)
and whole-word raw source column names. Failures identify file and line. The **only source
allowlist** is `app/schemas/common.py`'s literal membership check implementing input exclusion;
it must contain exactly the three exclusion tokens and no raw source token. Existing
negative/rejection payload tests are outside the production-source scan; test snapshots
are always scanned. No general file/directory exemption is applied to app code.

The proxy-wording guard scans these documents plus docs/*.md and README.md for phrases
that describe proxy predictions as established physical failures. There is no wording
allowlist. Error and user-visible recommendation text follow the same proxy interpretation.

## Coverage and regression checks

pytest-cov is a development dependency. Line coverage is required at >=80% both for
app/services and for app/repositories. The combined report has a configured 80% threshold,
and check_coverage.py independently enforces each package so one cannot hide the other's gaps.

```powershell
$env:TEST_DATABASE_URL = $env:DATABASE_URL
$env:MQTT_TEST_HOST = "127.0.0.1"
$env:MQTT_TEST_PORT = "51883"
.venv/Scripts/python.exe -m pytest -q -s --durations=20 --cov=app.services --cov=app.repositories --cov-report=term-missing --cov-report=json:.pytest_cache/phase8-coverage.json --cov-fail-under=80
.venv/Scripts/python.exe scripts/check_coverage.py .pytest_cache/phase8-coverage.json
.venv/Scripts/python.exe -m ruff check .
.venv/Scripts/python.exe -m ruff format --check .
```

All prior 648 test cases are retained without modification. New tests cover
500-row differential comparisons, prepared-plan safety, duplicate bypass and SQL counts,
request metadata/no-leak errors, every readiness backend and failure mode, compatibility
and name/wording guards, and real simultaneous HTTP batch/MQTT-style/replay ingestion.
The three-transport overlap test produces exactly 120 unique telemetry and analytics rows,
without duplicate active alert types, deadlocks or failed replay status.

The million-row disposable PostgreSQL fixture loads telemetry with generate_series and
one corresponding analytics row per telemetry row, then ANALYZEs both tables. It measures
actual HTTP responses for a 24h telemetry page, latest, four-signal 24h trends and a 24h
health page (cold plus five-sample median/max). This is test-only data, not a production
seed script. Final timings and coverage are recorded in the acceptance/performance docs.
